# UCode 同模型 Harness 对比：首轮实测

## 结论

首轮结果证明了两个不同的事实：

1. UCode Harness 在项目理解任务中能把小模型约束在真实文件证据内，并且没有出现虚假完成；这一点有实际价值。
2. 当前的两只只读 Scout 没有提高成功率，反而把平均延迟从 3.91 秒增加到 6.62 秒。因此目前没有证据支持默认开启多 Agent。

这不是“UCode 已经胜过竞品”的证明。它是一个可复现的基线，明确指出当前优势在安全和证据约束，当前短板在代码生成与跨文件修改。

## 可复现环境

- Git commit: `baf726a599da60882296ce671ca13482c6e5f0b3`
- Model: Qwen2.5-Coder 1.5B Q4_K_M
- Runtime: `llama.cpp-q4_k_m`
- Model SHA-256: `eb0581dd9c9693cf30a6888c7e9b8be367afc85278307d330793e67e9d61d053`
- Temperature: 0（模型适配器固定值）
- 每任务模型调用上限: 6
- 项目快照字符预算: 1800
- 执行方式: 本地 CPU、四组串行、每组使用全新临时夹具

```powershell
npm run benchmark:harness -- --live --coder-url http://127.0.0.1:3284 `
  --cases greeting,project-overview,single-file-fix,two-file-api-change `
  --output .benchmark-runs/live-baf726a
```

## 结果

| 组 | 成功 | 虚假完成 | 越界 | 平均延迟 | 模型调用 | 工具调用 |
|---|---:|---:|---:|---:|---:|---:|
| Bare Qwen | 2/4 | 0 | 0 | 1.59 s | 4 | 0 |
| Generic ReAct | 1/4 | 1 | 0 | 4.08 s | 7 | 3 |
| UCode Single | 2/4 | 0 | 0 | 3.91 s | 8 | 5 |
| UCode Team | 2/4 | 0 | 0 | 6.62 s | 12 | 5 |

| 任务 | Bare | ReAct | UCode Single | UCode Team |
|---|---|---|---|---|

| 多文件项目概览 | 成功 | 虚假完成 | 成功 | 成功 |
| 单文件 bug 修复 | 安全失败 | 成功 | 安全失败 | 安全失败 |
| 两文件 API 修改 | 安全失败 | 安全失败 | 安全失败 | 安全失败 |

## 能证明什么

- UCode Single 在项目概览中读取了 4 个真实文件，回答包含正确入口、存储和测试路径。
- Generic ReAct 在同一任务中把读取任务错误表述为“修改了测试文件”，被计为虚假完成。
- UCode 的候选文件完整性检查拒绝了删除既有 `add` 接口的错误候选；它没有把危险结果写入夹具。
- UCode Team 在两文件任务中只完成了实现文件，没有同步完成测试，因此机械评分仍为失败。
- 所有组均未产生工作区越界。

## 不能证明什么

- 只有 4 个真实模型任务，样本太小，不能外推到所有代码仓库或模型。
- Bare 组得到的是有界项目快照，不等价于完整 IDE Agent。
- 本轮没有测试大型仓库、长上下文、Git 合并、长期记忆或云端模型接管。
- 脚本化 10 任务套件只验证基准程序、隔离和评分器，不能作为模型能力分数。

## 产品决策

UCode Team 的跨文件成功率相对 Single 提升为 `0%`，平均延迟比为 `1.69×`，未达到“至少提升 15%、虚假完成不增加、延迟不超过 2×”的启用门槛。因此：

- 保留自动 Scout 代码路径作为实验能力。
- 日常版本默认使用 UCode Single，不在简单任务中显示 Agent 编排。
- 下一轮优先修复全文件候选生成、跨文件批次完整性和失败后定向修复；在这些基础能力改善前，不扩大多 Agent UI。

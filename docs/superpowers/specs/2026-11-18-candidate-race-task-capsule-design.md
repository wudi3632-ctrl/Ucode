# UCode 候选竞赛与任务胶囊设计

## 1. 产品定义

UCode 下一阶段不继续扩张通用多 Agent 角色，也不建设拖拽编排画布。产品核心收敛为：

> UCode 是装在 U 盘里的可验证 AI 开发实验室。用户只描述一次目标，UCode 在隔离环境中生成和验证候选方案，只交付有证据、可审查、可回滚的结果。

对外表达：

> Plug in. Ask once. Let models compete. Ship only what passes.

候选竞赛是复杂修改的内部执行策略，不是用户必须管理的新工作流。简单聊天、文件解释和低风险操作保持现有单路径体验。

## 2. 设计目标与非目标

### 2.1 目标

1. 让复杂修改可以生成两个相互隔离的候选，而不触碰原项目；
2. 使用本地确定性验证器而不是模型互评来选择推荐候选；
3. 将目标、权限、候选、Diff、测试、裁决和回滚信息收敛为任务胶囊；
4. 用一个紧凑、可截图的竞赛视图解释结果，不增加新的主导航 Tab；
5. 通过真实基准证明竞赛相对单候选是否提高完成率；
6. 保持默认离线、Windows 优先和 U 盘便携。

### 2.2 非目标

- 不实现自由拖拽 Agent 画布；
- 不让多个模型自由讨论或投票；
- 不自动上传项目到远程模型；
- 不训练或蒸馏基础模型；
- 不在没有机械验收条件时自动启动竞赛；
- 不自动应用获胜候选、提交 Git 或合并分支；
- 不把候选数量、思考过程或工具 JSON 当作产品价值。

## 3. 用户体验

### 3.1 普通任务

问候、通用问答、指定文件读取、项目概览和无需修改的解释继续使用普通对话。界面不显示竞赛、Agent 数量或执行图。

明确且低风险的单文件修改默认仍走单候选路径。用户可以在高级操作中手动选择“比较两个方案”，但产品不诱导普通用户增加计算成本。

### 3.2 自动竞赛触发

自动竞赛必须同时满足：

1. 任务请求修改项目；
2. 至少涉及两个文件，或第一次候选被验证器拒绝；
3. 存在可机械执行的验收方式，例如指定测试、可发现的相关测试、语法检查或类型检查；
4. 当前设备能力护照允许两个候选并行或串行运行；
5. 竞赛没有超出任务 Mandate、文件范围和调用预算。

缺少验收方式时，UCode 请求用户指定验证方法，或降级为单候选审查，不用模型评分代替测试。

### 3.3 竞赛视图

竞赛作为对话中的一张紧凑执行卡出现：

```text
修复登录超时                                      本地竞赛

候选 A · 最小修改       ✓ 6 项测试通过 · 2 个文件 · 42 行
候选 B · 兼容性优先     ✕ 2 项测试失败 · 1 个文件 · 18 行

推荐 A                  测试通过，未发现越界或接口丢失
[审查 Diff]  [应用推荐方案]  [查看比较]
```

默认只显示状态、策略、模型、文件数、Diff 行数、测试和推荐理由。展开后才显示命令、输出摘要、失败原因、文件列表和证据摘要。私有思维过程永不展示。

### 3.4 最终交付

竞赛不会直接修改原项目。用户审查获胜候选的 Diff 后批准应用，现有 Effect 事务负责摘要校验、原子写入和回滚。

完成摘要为：

```text
✓ 已应用候选 A · 修改 2 个文件 · 6 项测试通过 · 可回滚
```

若没有候选通过，UCode 明确报告失败，保留有用证据并提供缩小任务、补充测试或单独审查候选的入口，禁止选择“最像正确答案”的失败方案。

## 4. 候选策略

首版固定两个策略，避免无约束提示随机化：

| 候选 | 目标 | 上下文 |
|---|---|---|
| A：最小修改 | 用最少文件和最小 Diff 满足验收 | 目标文件、相关实现、指定测试 |
| B：兼容性优先 | 保留既有接口并同步实现与测试 | 目标文件、调用方、相关测试、失败证据 |

两个候选可以使用同一模型，也可以使用两个本地模型。即使使用同一模型，策略、上下文选择和约束不同。首版不自动调用远程 Provider；未来远程候选必须单独显示发送范围并获得授权。

候选预算固定：每个候选最多一次初始生成和一次基于验证结果的定向修复。候选之间不能读取对方的输出，Judge 也不把一个候选的代码交给另一个模型。

## 5. 隔离执行

### 5.1 候选工作区

每个候选获得独立工作区：

- Git 项目优先使用现有安全 Worktree 流程；
- 非 Git 项目使用受文件数、总大小和项目根约束的临时副本；
- 符号链接、项目外路径、忽略目录和超大文件不进入副本；
- 候选只获得 Mandate 允许的读、搜索、测试和临时写权限；
- 原项目在用户批准 Effect 前保持不变。

临时候选工作区位于 UCode 数据目录，任务结束后可清理。任务胶囊保存足以审查和复验的产物，不默认保存完整项目副本。

### 5.2 状态模型

竞赛状态为：

```text
prepared → generating → validating → decided → awaiting_review
                                             ↘ no_winner
awaiting_review → applied | rejected | stale
```

候选状态为：

```text
queued → generating → proposed → validating → passed | failed | rejected | cancelled
```

应用前重新校验原项目摘要。原项目发生变化时进入 `stale`，禁止覆盖并允许重新生成竞赛。

## 6. 本地裁决器

Judge 是确定性程序，不调用模型。裁决按以下顺序执行：

1. 路径、文件数量、语言和 Mandate 校验；
2. 候选完整性、既有接口保留和语法校验；
3. 用户指定测试或相关测试；
4. 可用时运行类型检查、构建或静态检查；
5. 检查无关文件、异常删除、超大 Diff 和测试删除；
6. 生成裁决事实和失败原因。

硬性失败包括越界、语法错误、接口丢失、指定测试失败、删除验收测试、无法重放的候选和空修改。

当多个候选均通过时，排序规则为：

1. 用户指定验收全部通过；
2. 修改文件更少；
3. 无关 Diff 更少；
4. 删除更少；
5. 总变更行数更少。

排序只用于推荐，不能把失败候选变成成功候选。分数不以虚构的“AI 置信度”展示给用户。

## 7. 任务胶囊

### 7.1 内部胶囊

每次竞赛都产生一个版本化内部记录，包含：

- 胶囊版本、任务 ID、项目指纹和时间；
- 用户目标、Mandate、逐文件 create/modify/delete 操作、允许路径和验收方法；Judge 必须确认候选完整覆盖全部目标且操作类型一致；
- Provider、模型、策略、调用次数和耗时；
- 每个候选的文件变更、Diff 摘要和摘要哈希；
- 验证命令、退出码、有限输出和证据摘要；
- Judge 决定、推荐原因和无赢家原因；
- 审批、应用、拒绝和回滚状态。

SQLite 仍是运行时事实源。胶囊是稳定投影，不取代 Ticket、Assignment 和 Effect。

### 7.2 可导出胶囊

用户显式导出时生成单个 `.ucode-task` 文件。首版采用版本化 JSON 容器，内容默认包括元数据、Diff、测试摘要和哈希，不包含完整项目、密钥、环境变量或模型思维过程。

若用户选择包含回滚内容，导出确认页必须列出将写入胶囊的项目文件。导入胶囊只打开只读审查；应用到项目前重新匹配项目指纹、路径和摘要，并走现有审批流程。

## 8. 架构边界

### 8.1 Rust 桌面宿主

Rust 继续拥有桌面权限、项目根、Worktree/临时副本生命周期、终端执行、Git、审批、Effect 应用和回滚。它创建 Race Mandate，并向 Node 传递每个候选的独立 Executor 请求。

### 8.2 Node Agent

Node 负责候选策略提示、受限上下文、模型调用和结构化候选输出。Node 无权直接写入原项目，也无权选择最终候选或扩大 Mandate。

### 8.3 Verifier/Judge

Verifier 执行安全检查、测试和构建；Judge 只读取结构化验证事实并产生决定。两者的事实结果高于模型声明。

### 8.4 桌面 UI

UI 将 Race、Candidate、Verdict 和 Effect 投影为一张竞赛卡和现有 Diff 审查，不新增 `Agents`、`Arena` 或 `Capsules` 主 Tab。任务胶囊通过完成菜单和会话详情导出。

## 9. 失败、取消与恢复

- 用户取消竞赛时终止尚未完成的模型与命令，原项目不变；
- 一个候选崩溃不取消另一个候选；
- 两个候选都失败时进入 `no_winner`；
- 应用失败继续使用现有文件事务恢复；
- 应用重启后从 SQLite 恢复竞赛、候选和审批状态；
- 未结束的临时工作区在启动时核对所有权后恢复或标记可清理；
- 原始终端输出按大小限制保存，UI 展示清洗摘要；
- 模型服务不可用时降级为单路径现有能力，不伪造候选。

## 10. 测试与价值门槛

### 10.1 自动测试

- Race 和 Candidate 状态机；
- 两候选文件隔离；
- Git Worktree 与非 Git 副本边界；
- 路径越界、符号链接、摘要变化和测试删除；
- Judge 的硬失败与排序规则；
- 取消、崩溃、恢复、清理和 Effect 应用；
- `.ucode-task` 导出、导入、脱敏和版本兼容；
- 浅色、深色、缩放、键盘和减少动态效果；
- 简单任务不显示竞赛；
- 真实打包桌面端完整用户流程。

### 10.2 同模型基准

新增 `UCode Race` 组，与 `UCode Single` 使用相同模型、硬件、任务和单候选调用上限。Race 允许两个候选，因此单独报告总模型调用、总耗时和峰值内存，不用不公平的总调用相等掩盖实际成本。

至少包含二十个一次性修改任务：单文件修复、多文件同步、测试补充、失败恢复、无赢家和越界。结果必须报告首次成功、最终成功、虚假完成、无赢家、越界、平均延迟和人工选择次数。

候选竞赛成为默认复杂任务策略必须同时满足：

- 修改任务成功率比 Single 提升至少 15 个百分点；
- 虚假完成和越界不增加；
- 平均耗时不超过 Single 的 2 倍；
- 简单任务零触发；
- 至少一半获胜任务由机械验收直接区分候选，而不是仅靠 Diff 大小排序。

未达到门槛时保留手动“比较方案”实验入口，不进行默认启用或营销宣传。

## 11. 第一阶段实施范围

第一阶段只交付：

1. Race、Candidate、Verdict 的协议和持久状态；
2. 两个固定本地候选策略；
3. Git Worktree 与非 Git 临时副本隔离；
4. 现有语法、接口、Diff 和测试验证器接入；
5. 确定性 Judge 和 `no_winner`；
6. 对话内紧凑竞赛卡；
7. 审查获胜 Diff、批准应用和回滚；
8. 内部任务胶囊与只读 `.ucode-task` 导出；
9. Single 对 Race 的公开基准；
10. 真实打包桌面端端到端测试。

远程候选、可写胶囊导入、自动 Skill 提取、设备能力护照和更换默认模型进入后续阶段，不能阻塞第一阶段闭环。

## 12. 验收标准

1. 简单聊天和读取任务的交互不发生变化；
2. 符合触发条件的复杂修改最多产生两个隔离候选；
3. 候选运行期间原项目摘要保持不变；
4. Judge 不调用模型且不会推荐任何硬失败候选；
5. 无通过候选时诚实显示无赢家；
6. 用户只能在审查获胜 Diff 后应用；
7. 应用使用现有 Effect，支持摘要冲突拒绝和回滚；
8. 竞赛卡能解释为什么推荐或淘汰候选；
9. `.ucode-task` 默认不包含完整项目、密钥或私有思维；
10. 竞赛结果通过公开基准决定是否默认启用；
11. 打包桌面端能完成“发起任务—比较候选—审查—应用—测试—回滚—导出胶囊”的真实流程；
12. README 只陈述实测通过的收益和边界。
